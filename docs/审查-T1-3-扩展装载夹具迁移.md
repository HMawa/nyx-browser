- 任务卡：`Nyx-PC主开发交接-1.20-v1.md` §5 T1（扩展验证脚本补档）
- 性质：**测试夹具过期**（产品代码是对的）
- 状态：已修，脚本 **25 项全绿**（原 18 通过 / 6 失败）；提交 `test(ext): 扩展装载夹具跟上 session.extensions 新命名空间，并钉死这条契约`

---

## 1. 现象（改前实测）

```
node scripts\verify-extensions.js
结果：18 项通过，6 项失败
  - 目录安装 MV2 扩展成功并自动启用 → false !== true
  - 扩展已复制进仓库（源目录可删） → Cannot read properties of null (reading 'dir')
  - 装载时向分区传 allowFileAccess 且路径为仓库副本 → Cannot read properties of undefined (reading 'options')
  - 停用扩展：从分区卸载 → Cannot read properties of null (reading 'id')
  - 重新启用：回到分区 → Cannot read properties of null (reading 'id')
  - 模拟重启：新实例按索引装载启用项 → 0 !== 2
```

交接单只记了最后一条（`0 !== 2`），实际是 6 条。

## 2. 取证（为什么不是产品 bug）

1. 第一条失败的断言是 `scripts/verify-extensions.js:253` 的 `assert.strictEqual(res.extension.loaded, true)`。
   而 `loaded` 只有一个来源：`src/core/extensions.js:524`，写在
   `await ses.extensions.loadExtension(...)` 成功之后。
2. 产品侧调用（`src/core/extensions.js:522` / `:551`）：

```js
const extension = await ses.extensions.loadExtension(item.dir, { allowFileAccess: true });
ses.extensions.removeExtension(item.runtimeId);
```

3. 假分区（`scripts/verify-extensions.js` 原 `createFakeSession()`）只实现了**旧写法**：

```js
async loadExtension(dir, options) { … }
removeExtension(id) { … }
```

把方法挂在 session 对象**本身**，没有 `extensions` 这一层。

4. 于是 `ses.extensions` 是 `undefined` → `loadOne` 抛异常 → `item.loaded = false`、
   `lastError` 记下 `Cannot read properties of undefined (reading 'loadExtension')`。
   后面 5 条全是从这里塌下去的：`res.extension.loaded` 为 false → `installedA` 没被赋值 →
   所有用到 `installedA.dir / .id` 的检查报 null；重启装载计数自然是 0。

5. 产品代码为什么是对的：Electron 45 把扩展 API 挪进了 `session.extensions.*`。
   运行时可观测证据（同一次测试输出）：

```
(electron) 'session.getAllExtensions' is deprecated and will be removed.
  Please use 'session.extensions.getAllExtensions' instead.
```

   也就是说真实环境里新命名空间存在、旧写法只剩告警。`verify-extensions-startup.js`
   在真实 Electron 里跑出「普通分区装载 1 个扩展 PASS」，进一步证明产品路径是通的。

## 3. 改动

`scripts/verify-extensions.js`（仅此一个文件）：

```js
function createFakeSession() {
  const loaded = new Map();
  const loadExtensionCalls = [];
  const loadExtension = async (dir, options) => { … };
  const removeExtension = (id) => { … };
  return {
    loaded,
    loadExtensionCalls,
    loadExtension,          // 旧写法保留：万一将来要兼容旧内核
    removeExtension,
    extensions: { loadExtension, removeExtension },   // 新写法：产品实际调的这条
  };
}
```

新增一条守卫（把"夹具与产品用同一套 API"变成断言）：

```js
check('装载走 Electron 45 的新命名空间 session.extensions.*', () => {
  const source = fs.readFileSync(path.join(__dirname, '..', 'src', 'core', 'extensions.js'), 'utf8');
  assert.match(source, /ses\.extensions\.loadExtension\(/);
  assert.doesNotMatch(source, /\bses\.loadExtension\(/);
});
```

为什么两边都挂：假分区两种形状指向**同一份实现**，调用方式与真实 API 一致；
守卫则钉住"产品必须走新命名空间"。这样下次谁改回旧写法、或谁把夹具改回旧形状，
都会有一条明确的红，而不是 6 条看不懂的 null 崩溃。

## 5. 这条修复能证明什么、不能证明什么

- **能**：`ExtensionManager` 的安装/启用/停用/删除/复条目更新/索引损坏兜底等逻辑在
  **真实 API 形状**下是对的；装载失败会如实写 `lastError` 而不是假装成功。
- **不能**：假分区毕竟是假分区，Chromium 真的会不会装 MV2/MV3，要靠
  `verify-extensions-startup.js`（真实启动）与 `verify-extensions-e2e.js`（真实注入）——
  这两个在 T1-1 / T1-4 里已经是绿的。

## 7. 夹具里为什么留着旧写法（有意，不是没清干净）

假分区 `createFakeSession()` 在挂了 `extensions: { loadExtension, removeExtension }` 之后，
**仍然把 `loadExtension / removeExtension` 留在 session 对象本身**，这是有意的：

1. 那个守卫断言「产品代码必须走 `ses.extensions.*`、不许走 `ses.loadExtension(`」，
   要证明这条守卫真的会红，夹具就必须同时具备两种形状；
2. 历史版本里 `src/core/extensions.js` 走过旧写法，留着旧挂点可以在回归里
   继续覆盖"如果哪天有人改回去，断言立刻红"。

代价是夹具看起来比真实 session 多两个方法——它本来就是个替身，不是模拟器；
真实形状由 `verify-extensions-startup.js`（真实启动）与 `verify-extensions-e2e.js`（真实注入）覆盖。
