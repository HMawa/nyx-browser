# 审查单 · T1-1 扩展启动自检：清掉 ELECTRON_RUN_AS_NODE

- 任务卡：`Nyx-PC主开发交接-1.20-v1.md` §5 T1（扩展验证脚本补档）
- 性质：**脚本自身缺陷**（不是断言过期，也不是产品 bug）
- 状态：已修，脚本 10 项全绿；提交 `fix(ext): 启动自检脚本清掉 ELECTRON_RUN_AS_NODE（红线 10）`

---

## 1. 现象（改前实测）

```
node scripts\verify-extensions-startup.js
共 5 项，失败 2 项
  [PASS] 隔离 profile 预置扩展成功
  [PASS] 索引内 1 条且为启用状态
  [FAIL] 主程序正常退出（退出码 0）
  [FAIL] 启动报告可解析
  [PASS] 主进程无未捕获异常
```

被测进程 stderr 末尾是纯 Node 的崩溃栈尾（`Node.js v24.22.2`），不是 Electron 的启动日志。

## 2. 取证（为什么是这个原因）

1. `scripts/verify-extensions-startup.js:116` 原代码：

```js
const run = spawnSync(electronBin, [ENTRY], { cwd: ROOT, encoding: 'utf8', timeout: 120_000 });
```

没有传 `env`，子进程**完整继承**父进程环境。

2. 本机环境实测：

```
ELECTRON_RUN_AS_NODE=[1]
NODE_OPTIONS=[]
```

3. `ELECTRON_RUN_AS_NODE=1` 会让 Electron 二进制退化成纯 Node 解释器：它会把 `ENTRY`
   当普通脚本执行，脚本里的 `require('electron').app` 拿到的是字符串路径而不是 app 对象，
   于是直接抛错退出 —— 主程序从来没起来，自然「退出码非 0」「报告文件没写」。
   这正是 `AGENTS.md` 红线 10 记的那条坑。

## 3. 改动

`scripts/verify-extensions-startup.js`（仅此一个文件，+15 行）：

```js
const childEnv = {
  ...process.env,
  NYX_USER_DATA: USER_DATA,
  ELECTRON_DISABLE_SECURITY_WARNINGS: '1',
};
delete childEnv.ELECTRON_RUN_AS_NODE;
check('子进程环境已清掉 ELECTRON_RUN_AS_NODE（红线 10）', !('ELECTRON_RUN_AS_NODE' in childEnv));

const run = spawnSync(electronBin, [ENTRY], { cwd: ROOT, env: childEnv, encoding: 'utf8', timeout: 120_000 });
```

两点说明：

- **只删这一个变量**，其余环境原样传递（不搞 `env: {}`，那会把 PATH 之类也抹掉）。
- 加了一条 `check(...)`：把「子进程环境必须干净」这件事本身变成可见断言，
  以后谁再把 `env` 漏掉，第一次跑就红，而不是等一个看起来像产品 bug 的假失败。

  [PASS] 主程序正常退出（退出码 0）
  [PASS] 启动报告可解析
  [PASS] 主窗口已创建
  [PASS] 普通分区装载 1 个扩展
  [PASS] 隐私分区零扩展
  [PASS] 索引状态仍为启用

项数从 5 变 10 的原因：主程序真的起来了、报告真的解析出来了，后面 5 条子断言
（窗口/普通分区/隐私分区/索引/无异常）以前因为 `report` 为 null 根本没跑。
**不是新增了 5 个检查点，是原来那 5 条终于被执行了。**

## 5. 为什么不按「过期断言」处理

这条读起来像"环境问题不重要"，但它不是：脚本拿不到被测进程的真实启动结果时，
`verify-extensions-startup.js` 就彻底失去意义（永远是红的，久了就没人看）。
按红线 10 修环境，才算让这条检查恢复功能。
