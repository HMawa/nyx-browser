## 1. 现象 1：e2e 用弃用 API，弹出主进程崩溃框

```
（屏幕上）Error
A JavaScript error occurred in the main process
Uncaught Exception:
Error: EPIPE: broken pipe, write
    at [kWritetoConsole] …
    at Session.getAllExtensions (…/browser_init:4:42720)
    at D:\Nyx-src\scripts\verify-extensions-e2e.js:77:43
```

`scripts/verify-extensions-e2e.js` 原来用 `session.getAllExtensions()`（旧写法）。
Electron 45 里它只剩一条弃用告警，而告警是往 stderr 写的。当这个脚本的输出被重定向、
或上层进程只读了一部分就退出时，这条"只是提醒"的写入会抛 `EPIPE`，
在主进程里被当成未捕获异常 → **弹框**。一条日志没人读了，不该把被测进程打断。

**改动**（3 处调用 + 1 处兜底）：

```js
report.normalExtensions = normalSession.extensions.getAllExtensions()…
report.privateExtensionCount = privateSession.extensions.getAllExtensions().length;
report.afterDisableLoadedExtensions = normalSession.extensions.getAllExtensions().length;

process.on('uncaughtException', (err) => {
  if (err && err.code === 'EPIPE') return;     // 只吞"管道断开"
  console.error('未捕获异常：', err);
  app.exit(1);                                  // 其它异常照旧打出并失败退出
});
```

只吞 `EPIPE` 一种：真正的未捕获异常还是要让脚本失败，不能顺手把错误藏起来。

## 2. 现象 2：PowerShell 不等 GUI 子进程，退出码读不到

实测 `EXIT=0`、日志末行 `E2E: PASS`、残留 electron 进程 0。

## 5. 边界（必须写清）

1. e2e 用的是临时目录里造的 MV2/MV3 夹具扩展，不是真实商店扩展；
   它证明的是"注入链路通"，不证明"某个具体扩展能用"。
2. 输出里会有一条 `Manifest version 2 is deprecated…` —— 这是 Chromium 对 MV2 的提示，
   夹具特意覆盖 MV2，属于预期输出，不是失败。
3. 这四步加起来约 1 分钟，全量回归总时长因此从约 9 分钟涨到约 10 分钟。

## 5.1 MV3 这一格原来不算数（2026-11-23 复核后收紧）

**第一版的口径是错的**，必须改：报告里 `installMv3.ok / loaded` 都是 true，但

- MV2 与 MV3 的夹具都在改 `document.title`，实测 `mv3Title` 是 `INJECTED-MV2` ——
  只能证明"MV2 最后写赢"，**不能证明 MV3 注入过**；
- 更关键：`pass` 的判定式里只有 MV2 / 隐私分区 / 停用三组，**根本不含 `installMv3.*` 与 `mv3Injected`**，
  也就是说 MV3 装载失败、注入失败，这条 e2e 照样打印 `E2E: PASS`。

收紧后的做法：

1. 两个夹具改成**互不覆盖的副作用**：MV2 写 `document.body.dataset.mv2 = '1'`（并保留改标题），
   MV3 只写 `document.body.dataset.mv3 = '1'`，不再碰标题；
2. `mv3Injected` 改成 `document.body.dataset.mv3 === '1'` 的真实读数（`mv3Title` 仍记进报告，但不再当判据）；
3. `pass` 里补 `report.installMv3.ok && report.installMv3.loaded && report.mv3Injected === true`。

实测：`E2E: PASS`、`mv3Injected: true`、`mv3Title: "INJECTED-MV2"` —— 两条注入同时成立且互不干扰。

**所以现在能说**：这条 e2e 证明「MV2 注入链路、MV3 注入链路、隐私分区零扩展、停用卸载链路」四件事；
**只能说**夹具扩展在这四条上是通的，不能说真实 MV3 商店扩展都能用。

## 7. 临时目录清理（原先一直在漏）

现象：每次跑完 `%TEMP%` 都多一个 `nyx-ext-e2e-<时间戳>` 目录，日志里只有一句
`（临时目录清理延后：EPERM）`，日积月累属于测试债。

根因不是"删得不够快"，而是**清理根本没跑到**：`scripts/verify-extensions-e2e.js` 里
所有窗口 `destroy()` 之后，Electron 的默认 `window-all-closed` 会**直接退出进程**；
而 `await cleanupWorkDir(...)` 在 destroy 之后，一 yield 回事件循环，进程就没了。
（顺带解释了两件事：为什么清理日志打在 stdout 上从来抓不到——`app.exit()` 会截断输出；
为什么"重试 5 次"这类改法一开始没用——它压根没执行。）

改法三条：

1. `app.on('window-all-closed', () => {})` —— 空监听，退出时机与退出码由脚本自己决定；
2. 清理仍然"本进程 5 次重试 → 失败就交给 detached 后台进程 2 秒后删"
   （`spawn(process.execPath, ['-e', helper], { detached: true, stdio: 'ignore', env: { ...process.env, ELECTRON_RUN_AS_NODE: '1' } })` + `unref()`；
   用 `ELECTRON_RUN_AS_NODE=1` 是因为 `process.execPath` 是 `electron.exe`，不这样会再起一个 GUI 进程）；
3. 开跑前先扫掉 5 分钟以前的同名目录（`sweepOldWorkDirs()`），保证不会无限累积；
   清理结论写进 `%TEMP%\nyx-ext-e2e-cleanup.log`（不靠会被截断的 stdout）。

实测：连跑两次，`%TEMP%\nyx-ext-e2e-*` 数量 **2 → 0**，日志里是
`已删 正常退出（后台进程 2 秒后再兜一次）`。
